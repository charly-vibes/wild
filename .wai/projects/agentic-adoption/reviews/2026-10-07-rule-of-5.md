## STAGE 3: CLARITY

This stage examines whether the experimental outcomes distinguish blocking, uncertainty, and unsafe acceptance, rather than merely producing a favorable aggregate score.

**[CLAR-001] MEDIUM — UNVERIFIED — linked design:136**

Description: "all missed breakages including refused/unknown outcomes separately" does not define whether an abstained or refused broken candidate counts as a missed breakage. Other sections correctly treat unsupported cases as abstentions, so the primary metric wording needs alignment rather than a new safety rule.

Impact: Implementers could report different false-negative rates for identical results or count conservative refusal as unsafe acceptance.

Recommendation: Define a decision table against the independent oracle: accept/reject/unknown/error crossed with compatible/incompatible, plus intentional authorized change as a separate task class. Report unsafe acceptance among accepted updates, detection recall, abstention coverage, false blocks of valid updates, and completed-update rate with explicit denominators. Distinguish a sampled test pass from global compatibility.

## STAGE 4: EDGE CASES

The principal boundary case follows from the original product goal: version labels and ranges disagree with a particular consumer's actual compatibility.

**[EDGE-001] HIGH — VERIFIED — linked design:95 and :168**

Description: The first-use workflow retains host bounds, and E5 says "do not relax host dependency bounds by default." That default is reasonable, but the protocol never specifies the opt-in range-change workflow or an explicit stratum of compatible candidates excluded by those bounds.

Scenario: A dependency's major-labelled release removes an API the consumer never uses. The existing range excludes it; the selected candidate may nevertheless satisfy this consumer and its full dependency closure. The reverse case is a patch-labelled release allowed by the range that removes a used API.

Impact: Wild may successfully classify a synthetic interface change without demonstrating that it can help complete the update the user actually wants. Unchanged host constraints can conceal all of the extra upgrade opportunity.

Recommendation: Test both directions of disagreement. In an isolated branch/environment, explicitly propose and apply the manifest change, run the host resolver, validate the resulting closure and actual artifacts, and execute an independent consumer oracle. Preserve non-compatibility constraints, including supported runtime/platform and organization policy. A major version must not disqualify a candidate solely by label, nor may structural passing erase a genuine constraint. Also distinguish a directly compatible update from an agent-assisted migration that changes consumer code.

Edge Case Coverage: FAIR for the update objective; broader dynamic-demand and checker-tampering cases are already present and are not new findings.

## Is the original value proposition still present?

Yes, in the original specs:

- `openspec/specs/wild/spec.md:19` forbids deriving compatibility verdicts from version strings.
- `openspec/specs/wild-compose/spec.md:23` defines scoped substitution including all new dependencies and transitive closure.
- `openspec/specs/wild-compose/spec.md:24` defines lineage selection inside its supported monotone model; conflicts may refuse rather than search.
- `openspec/specs/wild-adopt/spec.md:29` currently makes brownfield updates advice-only within host version ranges.
- `openspec/specs/wild-registry/spec.md:24` pins contract and artifact identities, while line 26 retains host packages, tags, and versions.

Thus, the existing design proposes replacing version labels as the basis for compatibility judgments, while keeping release names, immutable identities, and reproducible selections. It does not eliminate revision identity or replace Git. Its adoption spec is deliberately narrower than its native composition ambition, so progress beyond advisory checks needs an explicit designed transition.

The agentic context can strengthen the original objective: agents mine and enrich contracts, propose candidate updates, and construct consumer repairs or adapters; deterministic checks evaluate those changes. Agents are an execution and adoption mechanism. They do not require redefining the product as generic AI code review.

## Recommended Actions

1. Re-anchor a product-route matrix around: "How can a team complete more useful software updates with less manual compatibility reasoning, using checked consumer contracts rather than trusting version labels?" Retain the current mining/authoring matrix as a subordinate decision.
2. Compare existing update automation plus CI, a consumer-specific update assistant, a general agent-change checker, and a native contract resolver/platform. Add criteria for independently validated updates completed, compatible updates unnecessarily blocked, unsafe updates accepted, human minutes per update, time spent behind a desired compatible release, first-use burden, and agent-assisted migration cost. Keep semantic compatibility and other adoption policies distinct.
3. Add a proposed end-to-end update workflow: discover candidate -> check current consumer demand and all required dependencies -> propose direct update or explicit migration -> resolve/install actual artifacts in isolation -> independently validate -> emit a reviewable pinned change. This is a recommendation, not an implemented command or approved spec change.
4. Make an update-specific cohort central to E3/E5: misleading patch labels, harmless major-labelled changes, out-of-range compatible candidates, real runtime/platform constraints, transitive conflicts, dynamic unknowns, and agent-assisted migrations. Measure direct updates separately from migrations.
5. Fix CORR-001/CORR-002/CLAR-001 before interpreting comparative results. Keep checks and independent oracles protected equally across arms, judge reuse by measured outcomes, and define all metric denominators.
